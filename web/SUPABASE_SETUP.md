# إعداد Supabase لراجع واختباره

تم تجهيز الكود وملف SQL. الاتصال بمشروعك وتشغيل الترحيل لم يُنفذا؛ لا توجد قيم اتصال محفوظة في المستودع.

## القيمتان المطلوبتان

من نافذة **Connect** في مشروع Supabase انسخ:

1. **Project URL** إلى `VITE_SUPABASE_URL`.
2. **Publishable key** إلى `VITE_SUPABASE_PUBLISHABLE_KEY` (أو legacy anon فقط إن كان مشروعك يستخدمه).

ضعهما في `web/.env.local`، وهو ملف مستثنى من Git. لا تستخدم Secret key أو service_role.
لا ترسل القيم في المحادثة. إذا لم يكن الملف موجودًا، انسخ `.env.example` إليه ثم املأه بنفسك.
أعد تشغيل خادم التطوير بعد تعديل المتغيرات؛ Vite يقرأها عند بدء التشغيل.

المفتاح العام يظهر في حزمة المتصفح بطبيعته؛ حماية البيانات تتم عبر RLS. لا تضف أي مفتاح سري للتطبيق.

## إعداد الحسابات في لوحة Supabase

- Authentication → Providers / Sign In: فعّل البريد وكلمة المرور، وفعّل Confirm email.
- اجعل الحد الأدنى لكلمة المرور ثمانية أحرف من إعدادات المزود. التحقق في المتصفح لتحسين الاستخدام فقط؛
  سياسة المزود هي التي تفرض القوة على الخادم.
- Authentication → URL Configuration: اضبط Site URL على رابط تطبيقك المحلي الحالي، مثل
  `http://127.0.0.1:5173/`، وأضفه إلى Redirect URLs. أضف رابط النشر الحقيقي عند توفره.
- رابط تأكيد البريد يرجع إلى أصل التطبيق ومساره؛ عميل Supabase يتولى استعادة الجلسة.
- البريد الافتراضي له حدود إرسال؛ عند تأخر رسالة التأكيد افحص مجلد الرسائل غير المرغوب فيها
  وإعدادات البريد في مشروعك، دون تعطيل عزل البيانات.

## تجهيز قاعدة البيانات — يدويًا

افتح `supabase/migrations/001_init.sql` من جذر المشروع، والصق الملف كاملًا في
Supabase SQL Editor → New query ثم Run على قاعدة جديدة. اقرأ `supabase/README.md` أولًا
إذا كانت هناك بيانات سابقة. لم يشغّل المساعد هذا الملف.

تحقق من جدول review_drafts والقيود وتفعيل RLS وسياسات SELECT/INSERT/UPDATE/DELETE.
لا توجد بيانات تجريبية في الترحيل. ظهور صفوف في SQL Editor وحده لا يختبر عزل الحسابات.

## التشغيل

استخدم Node.js ٢٦ (البيئة التي جرى التحقق بها)، أو إصدارًا مدعومًا حسب engines في package.json.
داخل `web/`:

```sh
npm ci
npm run dev
```

بدون الإعداد تظهر رسالة Console واحدة بأسماء المتغيرات فقط، وتتعطل نماذج الدخول بدل انهيار التطبيق.

## اختبار يدوي بعد الإعداد

1. افتح إنشاء الحساب، أدخل بريدك وكلمة مرور قوية. أكد البريد ثم سجّل الدخول.
2. أول دخول يعرض مسودة فارغة، لا يرفع مسودة المتصفح السابقة تلقائيًا.
3. أدخل اسم مراجعة، ومتطلبين، واختر ملفًا من جهازك. تُرسل الأسماء فقط؛ المحتويات لا تُقرأ ولا تُرفع.
4. انتظر ظهور «حُفظت المسودة في حسابك.» ثم أعد تحميل الصفحة: يجب بقاء الاسم والمتطلبات وأسماء الملفات.
5. سجّل الخروج ثم الدخول: يجب استعادة المسودة. جرّب كلمة مرور خاطئة: تظهر رسالة عربية مفهومة.
6. سجّل الدخول من متصفح آخر بالحساب نفسه: يجب استعادة المسودة بعد التحميل.
7. استخدم حسابًا ثانيًا: يبدأ فارغًا ولا يرى مسودة الحساب الأول. راجع اختبارات RLS في supabase/README.md.
8. افتح تبويبين قبل التعديل؛ احفظ في الأول ثم عدّل في الثاني: يظهر تعارض دون الكتابة فوق النسخة الأحدث.
   خيار «تحميل النسخة المحفوظة واستبدال المدخلات الحالية» يتخلى صراحة عن المدخلات غير المحفوظة.
9. افصل الإنترنت وحاول الحفظ: تظهر رسالة فشل وتبقى المدخلات في الصفحة. أعد الاتصال ثم أعد المحاولة.
   إذا وصل الحفظ قبل انقطاع الرد، قد يظهر تعارض عند المحاولة؛ حمّل النسخة المحفوظة للتحقق.
10. «تجربة المثال» يحمل المثال ويحفظه كاختيار صريح. تقريره توضيحي؛ تغيير المتطلبات يمنع نسبته إلى مدخلاتك.

الحفظ سحابي غير متزامن؛ انتظر تأكيده قبل إعادة التحميل. يحذر المتصفح عند المغادرة أثناء وجود تغييرات
غير محفوظة. لا توجد مزامنة دون اتصال، ولا استيراد تلقائي للمفتاح المحلي القديم `raje3.review-draft.v1`.

## الاختبارات وحدودها

```sh
npm test
npm run test:integration
npm run build
npm run test:e2e
```

اختبارات المتصفح تستخدم العميل الرسمي مع HTTP fixture محلي، ولا تتصل بمشروعك ولا تشغّل SQL.
على macOS تستخدم Google Chrome المثبت. على الأنظمة الأخرى جهز المتصفح عبر `npx playwright install chromium`.
لقطات الحساب في design/shots/ مأخوذة من فحص يدوي للمتصفح عند عرضي 375 و1280؛ فُحص 320 أيضًا دون تجاوز أفقي.
اختبارات Playwright مجهزة ولم تعمل داخل بيئة التنفيذ بسبب منع تشغيل Chrome؛ تفاصيل ما نجح وحدوده في VERIFICATION.md.
الاختبار الحقيقي للبريد وPostgreSQL وRLS ينتظر القيم وتطبيق الترحيل.
